当前结论：尚未达到生产高可用。交付范围是现有 event/error 与新设计的 traces；用户允许通过 `ssh wr` 测试，禁止使用 Docker。traces 的接口、存储、SDK 和 CLI 仍是待实施方案，不能将 event/error 的测试结果归到 traces。

功能与架构依据分别为 [TRACES-SPEC](../design/TRACES-SPEC.md)、[TRACES-ARCHITECTURE](../design/TRACES-ARCHITECTURE.md)；全新上下文架构审查与使用 workflow:test 的测试分析见 [TRACES-REVIEW](../design/TRACES-REVIEW.md)。平台目标沿用 [OPERATIONS](../OPERATIONS.md)，当前代码和实际运行证据用于判定完成情况。

## 环境事实

`wr` 是 Ubuntu 24.04 x86_64，2 个 CPU、2015016 KiB 内存。当前仅取得一个主机访问入口，没有另外两个独立故障域的基础设施清单；未发现 `/dev/watchdog`。这些事实不支持跨主机或跨可用区验收。

本次在 `/opt/oneaster-validation.6fkfox52` 建立独立测试目录，使用 Node 26.9.0、Bun 1.4.4 与 PostgreSQL 18.6，以 nobody 用户运行临时数据库。Node 与 PostgreSQL 二进制放在该目录，PostgreSQL 未安装为系统服务。Node 的原生依赖 libatomic1 通过 Ubuntu 包安装。未使用 Docker，未执行整机重启、网络隔离、watchdog 或生产数据库故障。

三节点 TLS 测试在同一台机器上启动三个 PostgreSQL 进程，证明对应的连接、复制和进程故障行为；三个进程不构成三个故障域。测试产物保存在该目录的 `workspace/artifacts/production-ha/`，原始失败日志保留。

## 连接池预算修复

wr 的 20ms 冷准入诊断记录了建连 10.79ms、身份核对 7.10ms，随后角色设置超出剩余预算；失败发生在连接入池之前。`poolWaitMs` 的现有契约涵盖连接建立与身份检查，因此冷连接可以按截止返回不可用，不能要求任何机器都在首次 20ms 内就绪。

busy 测试现在只在准备阶段按统一 5 秒绝对截止轮询 readiness，成功一次立即结束，截止失败保留耗时、次数和原因；业务请求及竞争阶段不重试。第一条写入被 `pg_blocking_pids` 证实阻塞后才开始第二次写入及计时；原 20ms、150ms、overloaded 和首请求已确认断言保留。独立 TCP 黑洞测试覆盖短冷准入安全拒绝、无收据和 store.close 前 socket 归零；后续请求允许在未决连接核对阶段安全拒绝，不要求必然再次到达黑洞端点。

另有确定的生产缺陷：建连时的剩余准入时间被保留为数据连接的 `query_timeout` 与 `statement_timeout`，使连接入池后仍受错误的短 SQL 上界约束。修复仅让数据连接采用配置的 `statementTimeoutMs` 作为 SQL 默认值；建连与外层准入、操作总截止、cleanup 与 COMMIT 截止保持各自约束。无新增公开参数、环境变量或数据库迁移。

真实 PostgreSQL 回归先就绪，再由外部事务锁住 schema_version，直接观察目标后端等锁 350ms 后释放；poolWait 为 250ms，SQL 预算为 1000ms。旧代码在本地及 wr 均返回 ready:false，修复后返回 ready:true。独立只读审查使用 workflow:test 复核了预算与测试前置。

维护 unknown 回归另有可见性时序错误：驱动先返回未知，再异步清理数据库后端；同步等待期间，PostgreSQL 事务仍在 ProcArray 中，其他查询可能仍见到待删除的审计行。测试现在保留 150ms 操作截止、350ms 返回上界与 SyncRep 观测，先在原有 1500ms 预算内确认后端退出，再核对审计行已删除。返回上界通过后立即清除 450ms 应急取消定时器，清理验证由驱动自身完成，失败时仍由 finally 兜底。没有移除或放宽结果断言。[PostgreSQL 18 提交与同步等待顺序](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/access/transam/xact.c#L1455)

N-1 混合负载以现有候选基线为起点：500 event/error 每秒与 500 spans 每秒同时持续 10 分钟，event/error 和 trace 查询各 10 次每秒，分别测量 JSON、Protobuf 与 gzip。全部确认身份与实际唯一落库身份一致；正常声明负载下写 p99≤1 秒、读 p99≤2 秒，故障期间的失败和未知确认必须进入可用性计量。该负载数字是待测基线，不能据此为 wr 或其他机器承诺容量。

## 无 Docker 的实施顺序

1. 完成 traces 架构切片 A–D，保持 event/error 回归及四项工程门禁通过；先在隔离数据库验证版本 1→2 的有限兼容窗口及收口，不在现有数据库试迁移。
2. 取得三个故障域的 SSH 入口、主机/可用区绑定、数据盘、私网与 DNS/TLS、备份目标和 fencing 能力清单。当前 wr 的 CPU/内存不能直接作为整个生产拓扑的规格结论。
3. 使用原生 Linux 包与 systemd 部署应用、PostgreSQL/Patroni、etcd、入口和维护任务。秘密通过受限文件注入，沿用已有环境变量与低权限角色。现有 `ops/render.ts` 的应用资源是 Kubernetes 工件，不在 wr 执行，不将其当成原生 systemd 部署已经完成。
4. 在真实清单上逐个验证故障域、旧主 fencing、故障后持续容量与恢复后确认身份；使用独立拓扑观察器，不以执行命令成功代替故障生效。
5. 在隔离目录完成备份还原与发布/回退演练，准备可审阅的部署清单和实际证据；依项目规则取得生产部署授权后再切换流量。

额外两个故障域、可靠 fencing 与真实部署信息缺失时，可以继续代码实现和隔离测试，不能完成生产故障验收。原型或测试机器上的通过结果不改变这些前置条件。
