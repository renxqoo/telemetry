# PostgreSQL driver

`src/index.ts` exports the synchronous `createPostgresStore(options): TelemetryStore` factory and asynchronous `migrate(connectionString): Promise<void>` and `maintain(connectionString, options): Promise<MaintenanceResult>`. Factory creation does not open connections. The first operation or readiness check reconciles prior sessions before admission. Readiness allows this reconciliation to use its operation deadline before starting the separate `poolWaitMs` admission budget. Other operations include reconciliation in their admission budget. Cancellation, cleanup connection limits and per-cleanup deadlines still apply.

`PostgresStoreOptions` requires `connectionString`, `profile` (`development` or `ha`), `role` (`collector` or `query`), `instanceId` and `nodeId`. Use a stable, unique `instanceId` of 1–16 ASCII letters, digits, underscores or hyphens for each managed process slot. Do not share a slot between concurrently live processes. `nodeId` identifies the development physical node and incident context. Development declares `single_node` durability.

HA additionally requires `requireTls: true` and `physicalNodes`, an array of at least three unique `{ id, connectionString, cleanupConnectionString }` entries. Each entry must address a physical database node directly. The root `connectionString` is used by development; HA discovers a unique reachable primary through these direct endpoints when opening a data connection. A physical node's data and cleanup endpoint must address the same server and database. Connection strings must use verified TLS. Correct cross-zone placement, Patroni strict synchronous mode, valid primary fencing and routing remain deployment requirements; SQL inspection does not prove those properties. Unreachable nodes retain their pending backend budget. Initial startup requires successful reconciliation of every configured node; running instances may use the unique reachable primary while an old node is unreachable.

The migration connection must be an elevated administrative connection able to create roles, create the schema, grant PostgreSQL monitoring/signal roles, and assume `telemetry_owner`. Migration creates NOLOGIN roles `telemetry_owner`, `telemetry_collector`, `telemetry_query`, `telemetry_maintainer` and `telemetry_cleanup`. Deployments create separate LOGIN accounts and grant exactly the corresponding runtime group. Collector/query accounts must never own tables or have BYPASSRLS. HA data LOGIN accounts require `CONNECTION LIMIT` no greater than `maxConnections`; HA cleanup LOGIN accounts require `CONNECTION LIMIT` no greater than `maxCleanupConnections`. They must be non-superuser and must not hold unrelated telemetry roles. Database-level limits preserve the physical connection ceiling across client disconnects and process replacement. Use dedicated cleanup credentials; they can inspect and signal controlled database sessions and must not be exposed to HTTP callers. Maintenance uses the owner role through its separate administrative connection.

Concurrent pool expansion shares one bounded primary discovery. Each waiter keeps its own cancellation and admission deadline; cancelling a waiter does not cancel another waiter. Discovery uses the existing cleanup connection ceiling and ends during store shutdown.

After successful startup reconciliation, an unidentified failed connection is retained against its physical node. It does not force a new all-node startup scan or block a healthy primary on another node. Before expanding on a node with unresolved identities, the driver inspects the exact recorded application nonces on that node, transfers matching sessions to bounded backend cleanup, and keeps their connection budget until cleanup is confirmed. Store shutdown rejects late admission and closes data connections still being established. It waits for initialization and discovery, then drains cleanup tasks and takes over identified pending sessions in bounded batches. Each backend receives at most one attempt during that close, within the shutdown deadline; failed physical cleanup retains its debt.

| Option                    | Default                     | Meaning                                                                    |
| ------------------------- | --------------------------- | -------------------------------------------------------------------------- |
| `maxConnections`          | collector 10, query 5       | Data plus unconfirmed backend budget per physical node                     |
| `maxCleanupConnections`   | 2                           | Reserved cleanup connection ceiling per physical node                      |
| `poolWaitMs`              | 250                         | Bounded admission/connection wait                                          |
| `statementTimeoutMs`      | collector 500, query 1500   | Total data stage budget across rollback-safe retry                         |
| `lockTimeoutMs`           | 200                         | Individual lock wait ceiling                                               |
| `commitTimeoutMs`         | 1000                        | Independent monotonic COMMIT deadline                                      |
| `responseReserveMs`       | 25                          | Request budget reserved after COMMIT                                       |
| `cleanupTimeoutMs`        | 1000                        | Cleanup attempt deadline                                                   |
| `maxPendingCleanup`       | 2                           | Pending-backend admission ceiling per node                                 |
| `cleanupConnectionString` | development data connection | Development cleanup endpoint                                               |
| `onIncident`              | absent                      | Callback receiving `{code,nodeId,pending}` without payloads or credentials |

`poolWaitMs` bounds admission and connection establishment, including identity and role checks; a cold connection is allowed to fail within this budget. Data connections use `statementTimeoutMs` as their SQL default after admission. The remaining admission time is never retained as the session SQL timeout. Per-operation deadlines and transaction SQL budgets may impose shorter limits. Cleanup connections keep their own cleanup/discovery timeouts.

All operations receive the existing storage port `OperationOptions`, including an AbortSignal and absolute request deadline. A deadline/abort/notice/disconnect in COMMIT irreversibly returns `StoreError('confirmation_unknown', 'unknown')`. Before COMMIT, errors are `not_committed`. Conflicts include input indices and IDs. `storage_integrity_error` indicates an authorized, unexpired receipt without its matching event and must be surfaced as a storage failure. SQL failures are never converted to empty results.

Write SQL explicitly restricts receipt updates, fresh inserts and integrity checks to the current batch IDs, including before PostgreSQL has collected table statistics.

List limits are 1–500 items. A page's `next_cursor` is internal JSON for `PageKey`. The application signs and binds the external cursor. Every reader call returns only after its same-connection REPEATABLE READ query, audit insert and protected commit complete. Errors-only access cannot observe ordinary-event tombstones. Returned event projections never include receipt digests. `clock_skew_ms` is the immutable `received_at - occurred_at` difference in milliseconds; it includes transport delay and is not an authenticated clock diagnosis. It does not participate in payload digests, ordering, or retention.

`maintain` accepts `prebuildDays` (default/minimum 7), `batchSize` (default 1000, maximum 10000), `deadlineAtMs` (default 30 seconds from entry), and `lockTimeoutMs` (default 200). It takes a transaction-scoped distributed advisory lock, creates UTC daily partitions, drops only complete expired historical partitions, deletes a bounded batch of partially expired events, then eligible receipts, then audits. Lock contention returns `acquired: false` for advisory-lock contention; SQL lock deadlines reject the attempt. The absolute deadline covers connection admission, every data statement, and a protected synchronous COMMIT. Maintenance retains its separate administrative owner connection and uses the same independent COMMIT timeout, warning detection, and bounded backend cleanup as data operations. Its stable database-local session prefix includes each absolute deadline. A subsequent invocation preserves a predecessor that is still within its deadline and returns `acquired: false`; it reconciles expired predecessors before opening a new data connection. If expired-session cleanup fails, admission fails rather than resetting the physical backend budget across cron invocations. Administrative credentials must be able to inspect and signal the maintenance sessions created by earlier invocations. Pre-COMMIT failures roll back or discard the connection; a COMMIT deadline, notice, or connection failure rejects with `confirmation_unknown` and `unknown` outcome rather than returning maintenance counts. Provision maintenance at a cadence that prevents partition exhaustion and alert on failure.

Run the isolated integration tests with an empty administrative test database:

```sh
TELEMETRY_TEST_DATABASE_URL=postgresql://... node node_modules/vitest/vitest.mjs run --config packages/storage-postgres/vitest.config.ts
```

Tests modify privileges and install temporary deferred triggers, so the test database must be dedicated and not shared with live services. The repository integration runner supplies this environment. The suite runs on PostgreSQL 18 and validates public APIs and database isolation. The integration suite also runs `probes/tls-cluster.ts`, which creates and removes three local TLS nodes, using the binary directory in `TELEMETRY_PG_BIN`; it tests verified TLS, restricted roles, all-node session reconciliation, target mismatch rejection, synchronous-wait cancellation/backend bounds, and routing after promotion. Run it with `TELEMETRY_PG_BIN=/path/to/postgresql18/bin bun packages/storage-postgres/probes/tls-cluster.ts`; ports are allocated automatically unless `TELEMETRY_PG_BASE_PORT` supplies the first of three contiguous ports. A single-node pass does not establish cross-zone durability, availability, fencing, failover time or production throughput.

Trace storage uses contract/schema version 2: `span_receipts`, daily `trace_spans` partitions and independent `trace_query_audit`. Writes, duplicates, hidden-service conflicts and read audits reuse the protected synchronous transaction/unknown handling. A restricted SECURITY DEFINER confirmation function updates only receipt nonces in the current project/environment, validates its touched count, and exposes no hidden payload. Nanoseconds are numeric(20,0), uint32 flags use checked bigint, and safe JSON plus query columns are written in one transaction. Query byte estimates are verified against actual payload and metadata before the audit commits.

Maintenance prebuilds event and span partitions, deletes expired spans before tombstones, and retains independent trace audits according to policy. Results include spansDeleted, spanReceiptsDeleted and traceAuditsDeleted. Readiness also checks trace partitions, RLS, privileges and the confirmation function owner/search_path/PUBLIC ACL.

`db:migrate --prepare` opens the bounded 1/2 version window for existing event instances; `db:finalize` closes it to 2. `db:migrate --event-rollback` restores the old event version marker while preserving schema 2 and all trace data; trace ingestion must first be paused and new trace query/maintenance kept running. Use the documented release window and finalize again after forward repair. See `docs/implementation/TRACES.md`; no production migration is performed by tests.
